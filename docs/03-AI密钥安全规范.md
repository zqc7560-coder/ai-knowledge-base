# AI 密钥安全规范（强制红线 · Code Review 检查单）

> 适用：AI 智能知识库管理系统。本文件是 `01-项目总体计划.md` §7 的执行细则。
> 原则：**密钥只活在服务端进程环境里；前端、浏览器、仓库、日志、文档永远看不到它。**

## 1. 密钥当前存放位置（本项目实况）
- 真实值：`backend/.env`（已被 `.gitignore` 排除）中的 `AI_API_KEY`，以及本机 Hermes profile 的 `.env`。
- 该 key 已通过聊天明文传输过一次 → **上线前必须在阿里云百炼控制台重新生成并轮换**，旧 key 作废。
- 轮换操作有专用脚本（M11.2）：`bash scripts/rotate-ai-key.sh [--from-file 新key文件]`
  —— 新 key 从文件/getpass 进入，绝不落命令行/回显；改 `backend/.env` 与 `deploy/.env` →
  重启后端 → `ai-check` 验证；验证失败自动回滚旧 .env（"无法验证"不触发回滚，防误判事故）；
  用后按脚本提示清理含旧 key 的 `.env.bak.*`。

## 2. 硬性红线（违反 = 阻断合并）
| # | 规则 | 执行手段 |
|---|---|---|
| L1 | 任何文件不得含明文密钥（含注释、测试数据、文档、README） | pre-commit gitleaks 全仓扫描；CI `scripts/check-secrets.mjs` |
| L2 | `.env`、`*.local.*`、`deploy/secrets/` 不得进 git | `.gitignore` + gitleaks 兜底 |
| L3 | 前端不得出现任何 AI 服务 base_url / key（Vite 只允许 `VITE_API_BASE=/api` 这类非敏感变量） | 构建后扫描 dist：`grep -R "sk-\|api-inference\|dashscope" dist` 命中即 fail |
| L4 | 后端只有 `kb-rag.AiClientFactory` 可读 `AI_API_KEY`、可把它拼进外发 `Authorization: Bearer`；其他模块禁止读取/拼接（开放 API 解析用户自带 key 的 `Bearer ` 前缀属入站语义，不触碰 AI 密钥，selfcheck 6c 把关） | `security-selfcheck.sh` 6a/6b/6c 三层审计（密钥持有唯一/外发拼接唯一/Bearer字样不混触密钥）+ Code Review |
| L5 | 任何 API 响应体/DTO/异常信息不得含密钥或其片段（尾 4 位掩码仅允许出现在 admin 配置页） | VO 白名单 + review |
| L6 | 日志不得打印 Authorization 头、请求体中 key、env dump；logback 加脱敏 converter（匹配 `sk-[A-Za-z0-9._-]{8,}` → `sk-***`） | logback 配置 + 集成测试断言 |
| L7 | 不把 key 贴进 curl 命令行历史 / shell 脚本明文；本地用 `source .env` 注入 | 开发习惯 + review |
| L8 | 生产环境经 docker secret / K8s Secret / CI masked variable 注入，compose 文件只引用变量名 | deploy 模板审查 |

## 3. 运行期防护（防"用户看到"的攻击面）
1. **无透传端点**：系统不存在任何"代理调用 AI 上游"的公开 API；问答出口只有 `/api/chat/ask`，输出为业务内容。
2. **SSE 断流安全**：上游异常时只回业务错误码（如 `AI_UPSTREAM_BUSY`），不回显上游原始报文（防止 provider 报错信息带 request 头）。
3. **限流省额度**：未登录 0 次；登录用户 20 问/分 + 每日 token 配额（Redis 计数）。异常流量直接 429，不转调用。
4. **审计**：`ai_usage_daily` 按用户记账；admin 页可查。发现盗用迹象 → 轮换密钥（流程：控制台建新 key → 改服务器 env → 滚动重启，业务无感）。
5. **浏览器侧**：token 走 Authorization header（非 Cookie localStorage 可讨论；MVP 用 header+Pinia 内存+刷新续期）；XSS 是 token 大敌 → 所有 MD 渲染过 DOMPurify。

## 4. 泄漏应急预案
1. 立即在百炼控制台禁用/轮换该 key（5 分钟内完成，仅改服务端 env）。
2. `git filter-repo` 清洗历史并强推（若曾误提交）。
3. 复盘：gitleaks 为何没拦住 → 补规则。
4. 检查异常用量账单（usage 日报）。

## 5. Code Review 检查单（每个 PR 自问）
- [ ] 新增 env 变量是否进了 `.env.example` 占位符而非真值？
- [ ] 新接口返回的 VO 里有没有直接把配置对象整个序列化出去？
- [ ] 日志新增字段是否可能带出 header/body？
- [ ] 前端代码有没有"图方便"直连 dashscope 域名？
- [ ] 测试文件用了真实 key 而非 `test-dummy-key`？
